# Spec — spec-003 后台手动上传候选图标

- 状态：**PASS**（2026-11-04，独立验收；首轮 3 项反例修复后复验；见 `acceptance.md`）
- 档位：FULL
- 关联：`spec-001`、`spec-002`、`constitution/tech-stack.md`

## 背景

候选图目前只能由运维把 `NN_名称.png` 放进 `toupiao/assets/icons/` 后重启服务。
2026-11-04 用户追加了 11 张图（已导入，当前 31 张），并明确要求：

> 在管理后台加一个手动上传图片的功能

目标是让管理员在 `/admin` 直接上传 PNG，立即出现在前台候选列表，不用 SSH、不用重启。

## 目标

1. 管理后台新增「上传图标」：支持一次选多张 PNG、逐张上传、显示成功/失败。
2. 上传后立即刷新图标列表（服务端重扫白名单），前台 5 秒轮询自动出现。
3. 服务端强制校验：管理员权限、PNG 内容、单文件大小、文件名、ID 唯一、数量上限。
4. 上传文件落到 `ICONS_DIR`，与现有 `NN_名称.png` 规则一致；Docker 卷改为可写并文档化。
5. 不破坏现有投票、用户、开关、导出；已有票数不受新增图标影响。

## 非目标

- 不做图标删除、排序、重命名、替换（本次只上传新增）。
- 不做图片裁剪/压缩/格式转换；上传什么 PNG 就存什么。
- 不做多管理员并发编辑冲突的复杂 UI；服务端保证 ID 不冲突。
- 不改投票规则与数据模型。

## 当前行为

- `scanIcons(ICONS_DIR)` 在启动时扫描一次；不重启看不到新文件。
- `docker-compose.yml` 把 `./assets/icons` 以 `:ro` 挂载，容器内无法写入。
- 管理后台只有数据/开关/钉钉配置，没有图标管理。

## 目标行为

### 管理员

1. `/admin` 新增「上传图标」面板：
   - 文件选择（`accept="image/png"`，`multiple`）；
   - 显示已选文件与大小；
   - 「开始上传」按钮；上传中禁用；
   - 每个文件的状态：等待/上传中/成功（显示新编号与名称）/失败（中文原因）。
2. 全部完成后：
   - 成功数量提示；
   - 后台图标数/表格自动刷新；
   - 前台下一次轮询出现新图标，票数 0。
3. 失败不阻塞其它文件：逐张上传，单张失败只标记该张。

### 上传规则

- 仅管理员；员工 403、未登录 401。
- 仅 `image/png`，校验 PNG 签名与结构（IHDR/IDAT/IEND）；只有签名、截断文件返回 400。
- 单文件 ≤ 5 MB；超过返回 413。
- 文件名：取原始文件名（去 `.png`、去可选 `NN_` 前缀），去除路径分隔符/控制字符/
  `..`/首尾空白，长度 ≤ 40；为空则用 `新图标`。
- 编号：在 01–99 中取当前未使用的最小两位编号；没有空位返回 409 `ICON_LIMIT_REACHED`。
- 落盘名：`NN_名称.png`；写临时文件后 rename，失败清理临时文件。
- 保存后重新扫描并替换内存中的图标白名单；返回新增图标与总数。
- 并发上传：串行化分配+落盘，不允许同编号冲突。

### 后台展示

- 面板显示当前图标数与上限 99；
- 不展示/不修改已有图标文件名；
- 上传成功立即更新，不需要整页刷新；
- 窄屏单列、无页面横向滚动。

### Docker / 运维

- `docker-compose.yml` 图标卷改为可写：`./assets/icons:/app/assets/icons`（去掉 `:ro`）。
- 文档说明宿主 `assets/icons` 需对容器内 uid 1000 可写
  （`sudo chown -R 1000:1000 assets/icons`）。
- 镜像仍不 COPY 图标；上传内容只存在宿主目录/卷中，不入库。

## 边界条件

- 上传同名文件：允许，分配新编号，名称可重复。
- 原始文件名含中文/空格/括号：保留可读部分，URL 仍由服务端编码。
- 原始文件名 `32_测试.png`：去掉前缀后名称为「测试」，编号按当时最小空位分配。
- 上传非 PNG（改后缀的 JPG/文本）：400 `INVALID_IMAGE`。
- 0 字节/截断 PNG：400。
- 超过 5MB：413。
- 图标目录不存在：上传时创建；创建失败/不可写返回 500 并提示目录权限。
- 已有 99 个图标：409，提示上限。
- 上传过程中服务重启：已 rename 的文件保留，未完成的临时文件启动时清理（或忽略）。
- 投票关闭时仍可上传（候选管理不受投票开关影响）。
- 管理员上传后，后台 state/前台 state 立即/轮询可见。
- 并发上传 2 张：编号不同，均成功。

## 技术约束

- 不新增运行时 npm 依赖。
- 上传走 `POST /api/admin/icons?filename=<urlencoded>`，请求体为原始 PNG 字节
  （不走 multipart，避免引入解析库）。
- 复用 `http.js` 的 Origin/安全头/错误体；新增 `readBodyBuffer(limit)`。
- `icons.js` 的 store 增加 `reload()` 与 `allocateId()`；扫描规则保持 `^(\d{2})_(.+)\.png$`。
- 前端不引入 UI 库；复用现有面板/按钮/主题。
- 测试：node:test 覆盖权限/校验/编号/并发/重扫；E2E 用临时图标目录，覆盖真实上传并断言前台出现。

## 兼容性要求

- 现有 31 张图标与投票数据不变。
- 上传新增后，图标总数/排名/票数计算正常；已有票数不丢。
- Docker 未配置/已配置钉钉均可上传；非 root 用户有写权限时正常。
- 桌面 1440 / 移动 375 可用。

- [ ] A2 选择 1 张 PNG 上传成功，落盘为 `NN_名称.png`，返回编号，前台轮询出现且 0 票。

- [ ] A5 编号取最小空位且并发上传不冲突；超过 99 返回 409。
- [ ] A6 上传后无需重启，后台/前台均看到新图标；已有投票数据不变。
- [ ] A7 `npm test`、`npm run build`、`npm run test:e2e` 全绿；E2E 覆盖上传。
