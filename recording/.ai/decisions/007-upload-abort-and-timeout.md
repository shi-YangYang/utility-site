# Decision 007 — 上传中断与超时的资源回收

## Context

第一轮验收（见 `specs/spec-001-mvp-recording-collection/acceptance.md`）判定 FAIL：
上传中途断线会导致 `DATA_DIR/tmp/` 留下半截文件、并让进程永久持有该文件的写 fd，
连续 3 次中断即累积 3 个文件 + 3 个 fd，只有重启才清。
违反 Spec「边界条件」中"请求中断或超时不得留下半截文件或索引记录"。

返工修复后产生了若干值得固化的工程约束，一处新增状态码，需要留痕。

## Decision

**一、中断判定依据是"请求体是否收完"，而不是"`close` 事件是否触发"。**

Node ≥ 16 里 `req` 的 `'close'` 在请求体**正常收完**时同样触发。
因此判据用 `req.complete === false` 才等价于"请求体没收完、对端走了"。
若无条件把 `'close'` 当断线，会把"已经收完、正在转码落盘"的好数据误判掉。

**二、资源释放的顺序是"先关写流，再删文件"。**

反过来的话，fd 会一直挂在已删除的 inode 上——在 FUSE 挂载目录上直接表现为
盘上残留 `.fuse_hidden*` 文件加一个指向 `(deleted)` 的写 fd。
这是一条**独立于断线**的残留路径：畸形表单（`Content-Length` 完整、multipart 被截断）
正常返回 400，但同样会漏。返工时一并修掉。

**三、主动 `bb.destroy()` 之前，必须先给每个文件流挂 `error` 监听。**

busboy 1.6.0 的 `Multipart._destroy()` 会带着错误 destroy 掉当前活跃的 `FileStream`
（`Unexpected end of file`）。没有 `error` 监听就是未处理事件，**会直接把进程带崩**。
这是实测踩到的坑，不是理论风险。

**四、超时：空闲 30 秒 + 请求体接收总时长 60 秒，硬编码为常量。**

- 空闲超时：`req` 上连续 30 秒无任何字节，视为对端已死。
- 总时长超时：请求体接收阶段的硬上限，覆盖"一直在慢速传、永远传不完"。
- 两个时限**只覆盖请求体接收阶段**。`parserFinished` 一落地就清除定时器，
  之后的转码、落盘、索引写入不受上传时限打断——否则可能停在写盘中途。

常量写在 `server/routes/employee.js` 顶部，**没有做成环境变量**（见下）。

**五、超时返回 `408 Request Timeout`。**

Spec 初版只定义了 400/401/413/415/500，未规定超时该回什么。
选 `408` 是因为语义最准确，且与 Node 自身 `server.requestTimeout` 的行为一致。
已回写进 `spec.md` F4 的补注。**对端已断线时不回写任何响应**（已无人接收）。

## Reason

- 这条缺陷的本质是"请求生命周期缺少中断出口"。补上出口后，中断、超时、畸形表单
  三条路径共用同一套收尾逻辑，比在每个分支各写一遍清理更不容易漏。
- 判据选 `req.complete` 而不是事件名，是因为事件语义随 Node 版本演进而误判成本高。
- 资源释放顺序（先关流后删文件）是 POSIX 语义决定的硬要求，不是风格问题。
- 时限只覆盖接收阶段，是为了区分两类失败：「上传没传完」（可以放弃）和
  「已收完但本地处理失败」（不能半途放弃，否则可能留下半个产物）。

## Alternatives

- **把超时做成环境变量**：被否决（本次）。`README.md` 的环境变量表是逐项对照
  `config.js` 写的，加两个开关就要同步改 README 与 `.env.example`。
  MVP 的正常上传只有几 MB，办公室网络远用不到 60 秒。将来若真出现
  "慢速链路 + 大文件"的合法场景（例如把 `MAX_UPLOAD_MB` 调到几百 MB），
  再改成环境变量即可——改的是 `employee.js` 顶部两个数字。
- **超时返回 400**：被否决。400 表达"请求本身有错"，而超时是"对端太慢或已死"，
  语义不同；且 408 与 Node 内置行为一致。
- **不做超时，只处理断线**：被否决。Spec 原文明确写了"请求中断**或超时**"。
- **在请求体收完后也保留时限**：被否决。会把转码/落盘半途掐断，反而制造新问题。

## Consequences

- **`408` 是 Spec 状态码表中新增的一项。** 已回写进 `spec.md` F4 的补注，
  并注明是本轮返工补入的。
- **超时时长是硬编码常量，不是配置项。** 使用方若需要调整，改
  `server/routes/employee.js` 顶部的 `UPLOAD_IDLE_TIMEOUT_MS` /
  `UPLOAD_TOTAL_TIMEOUT_MS` 两个常量。这是一个已知的、有意留下的技术债。
- **"上传成功但客户端没收到响应"的语义**：请求体已完整收完、转码落盘途中客户端
  才断开时，服务端**照常保存**，只是不回写响应。这是有意的——那属于
  "上传成功但没收到回复"，保存对员工更有利；索引写入严格在所有校验之后且原子，
  不会产生"半截记录"。
- 每次中断会打印一行 `log.info`。被反复触发时会产生相应日志量，换来可观测性。
- **空闲超时基于 TCP 字节流**。极端情况（本机磁盘卡顿导致 30 秒以上无 `data`）
  可能误判为超时；但此时上传本身也已不可用，代价可接受。
