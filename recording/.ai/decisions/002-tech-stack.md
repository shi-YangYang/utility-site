# Decision 002 — 技术栈选型

## Context

项目需要：一个接收文件上传的服务端、两个网页（员工端 / 管理端）、
把浏览器录音转成规整 WAV 的能力。规模极小——两个页面、约十个接口。

## Decision

- 后端：**Node.js 内置 `http` 模块**，不引入任何 Web 框架。
- 语言：JavaScript，不用 TypeScript（不引入构建步骤）。
- 前端：**原生 HTML / CSS / JS，零构建**，无打包器。
- 唯一运行时依赖：`busboy`（multipart 表单流式解析）。
- 媒体处理：调用外部 **ffmpeg** 可执行文件。
- 存储：文件系统 + JSON 索引，**不引入数据库**。

## Reason

- 规模上不需要框架。这个后端预计几百行，用内置 `http` 可以整个读完，
  比引入 Express/Koa 再加中间件链路更省心。
- 零构建让"克隆下来 `npm install && npm start` 就能跑"成为事实，
  也避免了 `node_modules` 之外的构建产物和 lockfile 复杂度。
- 唯一必须自己解决的是 multipart 解析——Node 内置没有，所以引入 `busboy`
  （流式、无传递依赖、体积小）。这比引入一整个框架划算得多。
- 存储用文件 + JSON 索引：数据量是"几十到几百人、各两个 WAV 文件"，
  数据库带来的运维成本和依赖都比收益大。索引写入通过原子写 + 串行化保证一致性即可。

## Alternatives

- **Express / Fastify**：被否决。框架带来的路由与中间件能力在这个规模下用不上，
  却引入依赖树与版本维护成本。
- **Python + FastAPI**：被否决。若下游音色分析用 Python 生态，统一语言有优势；
  但本子项目只负责收集，与下游解耦，且前端零构建的诉求使 Node 更省事。
  用户 2026-09-15 明确选择了 Node。
- **React / Vite 前端**：被否决。两个静态页面引入构建链路得不偿失。
- **SQLite**：被否决。当前记录量级下，文件 + JSON 索引足够，
  且能让下游直接 `ls data/recordings/` 拿到数据。

## Consequences

- multipart、静态文件、Range 响应、cookie 会话等都需要手写。
  这些在 `plan.md` 里已经列明实现要点。
- 依赖极少，升级与安全面很小。代价是未来若需求大幅膨胀（如账号体系、
  复杂查询），可能需要重新评估——届时按根规范第 21.4 节走目录/架构变更流程。
- ffmpeg 成为唯一的重外部依赖，必须做启动自检。
