# Decision 009 — 录音启动的并发守卫（spec-002 返工产物）

## Context

spec-002 第一轮独立验收判 FAIL：功能需求 E7「同一时刻只允许一段处于录音状态」
在 `getUserMedia` 的等待窗口内不成立。

首次授权弹窗（每个新员工第一次都会遇到）或慢设备会让 `getUserMedia` 挂起
数百毫秒到数秒。原实现把守卫（`segment.recording || state.busy || isAnyRecording()`）
放在 `await` **之前**，等待期间三者都还没置位、按钮也还没禁用，于是：

- 同一段正常双击 → 两次 `getUserMedia`，第一条流无人停止，留下常驻 `live` 的
  麦克风轨道（隐私指示灯持续亮、录音器继续缓冲）；
- 等待窗口内先后点两段 → 两段同时「录音中」，直接违反 E7。

该缺陷在 spec-001 的代码里同样存在（不是 spec-002 引入的回归），但 E7 是
spec-002 的明确要求，因此按验收结论返工。

## Decision

1. **同步守卫**：进入 `startRecording` 后立刻置 `state.starting` / `segment.pending`
   并调用 `updateUI()`（两段录音按钮显示"准备中……"并禁用），然后才 `await getUserMedia`。
2. **await 后复校验**：流拿到后再次检查是否已有录音；若窗口期内被别人抢先，
   立即 `track.stop()` 释放刚拿到的流并放弃本次启动。
3. **失败路径必须复位**：授权拒绝、录音器构造失败、被放弃等所有路径，都在
   `finally` 中释放未交接的流、清除 `starting/pending` 并刷新界面，
   不允许按钮永久卡在"准备中"。
4. **提交可用性同步排除等待期**：`canSubmit` 增加 `!state.starting`。
5. 以上守卫**不改变任何音频约束与产物格式**：EC/NS/AGC 仍为 false，
   流的获取与录制方式不变。

## Reason

- 竞态窗口由浏览器授权 UI 决定，用户无法感知"正在等待"，重复点击是自然行为；
  守卫放在 `await` 之后等于没有守卫。
- 只禁用被点击的那个按钮解决不了"先后点两段"；必须两段都禁。
- 失败路径不释放流会造成麦克风被长期占用（可复现的实际副作用），
  且是比"按钮状态"更严重的资源泄漏。

## Alternatives

- **只禁用被点击的按钮**：被否决，挡不住先点中文再点英文。
- **debounce / 时间窗去重**：被否决，授权等待时长不可预测，时间窗不可靠。
- **等待期不显示状态、静默忽略重复点击**：被否决，用户会以为没点上而继续点。
- **把守卫做成一个全局 mutex 包装 getUserMedia**：本次不需要；
  录音入口只有两段按钮，显式标志足够，引入通用锁反而增加维护面。

## Consequences

- 授权等待期两段录音按钮显示"准备中……"并禁用，提交按钮同时禁用；
  授权被拒后必须回到可点的「开始录音」（已有验收反例覆盖）。
- 后续任何新增录音入口（例如将来增加段落）都必须遵守同一守卫。
- 改动 `startRecording` / `updateUI` / `canSubmit` 后，必须复跑竞态用例：
  见 `specs/spec-002-ui-ux-polish/acceptance.md` 第二轮 R1–R5 与「Regression Risks」。
