# Decision 008 — UI/UX 与流程优化的方向与取舍

## Context

Phase 1（spec-001）已交付：核心功能（口令 → 姓名 → 录音 → 提交 / 管理端查看）
完整可用。用户 2026-09-15 判断"剩下的是 UI/UX 与使用流程的优化"，
并把本项决策权**全权交给协调 Agent**，要求起草 spec-002。

项目约束（`.ai/decisions/002`、`004`、`007` 与 `constitution/tech-stack.md`）：
无框架、零构建、运行时依赖只有 `busboy`、音频后处理必须全关、
口令只在服务端校验。可选项因此被压缩到"纯前端 + 不新增依赖"。

## Decision

1. **spec-002 是纯前端改动**：只动 `public/` 下的 HTML / JS / CSS 与文档；
   不改服务端、不改接口与数据模型、不改 `content/`。
   实施中若发现必须动服务端，停下报告，不自行扩范围。
2. **提交改用 `XMLHttpRequest`** 以获取真实上传进度（`upload.onprogress`）
   并提供"取消上传"；`fetch` 拿不到上传进度。错误语义（401/408/413/500）
   与覆盖规则保持不变。这是唯一被换掉的技术实现。
3. **新增录音电平与静音提示，但用只读 `AnalyserNode`**：
   麦克风流一路进 `MediaRecorder`（不变），另一路只做可视化分析，
   不加入录制、不新增约束；Web Audio 不可用时静默降级。
   目的：让"麦克风没声"在录音中就暴露，而不是录完试听才发现。
4. **姓名记忆用 `localStorage`；口令绝不持久化**（不写 localStorage /
   sessionStorage / URL / cookie）。姓名是内部协作信息、存在用户自己设备上，
   风险可接受；口令留在内存是既有安全约束（`.ai/decisions/003`）。
5. **管理端自动刷新用 30 秒轮询**，`document.hidden` 时暂停、可见时立即刷新，
   并提供开关。理由：现有接口足够，不新增推送机制（SSE/WebSocket 是过度设计）。
6. **时长判定以产物实际时长为准**（`Audio` 元素元数据，取不到时回退估算），
   修正 spec-001 验收报告中的回归风险 3。
7. **明确不做**：打包下载（需要 zip 依赖）、暗色模式、移动端专门适配、
   断点续传/分片、员工名单/未交视图。

## Reason

- 核心价值是"员工顺利交、管理员看得清"。上面每一条都对准现状盘点中的
  具体浪费（白录一轮、假进度、无法回改姓名、找不到记录），
  不是为了好看而改。
- 守住"零构建 + 无新依赖"的底线，改动范围可圈在 `public/` 内，
  回归面清晰、可自动化验证。
- 拒绝 SSE/WebSocket：单管理员、30 秒级时效完全够用，引入长连接会带来
  新的连接生命周期与资源回收问题（本项目刚在 spec-001 为上传生命周期还过债）。
- 拒绝打包下载：`zip` 会打破"运行时只依赖 busboy"的约束，
  而下载需求可以逐个文件满足。

## Alternatives

- **保留 `fetch`、进度条继续模拟**：被否决。模拟进度在慢网络下误导用户，
  且"取消"能力无从谈起。
- **引入前端框架（React/Vue）重写**：被否决。违反零构建约束，
  两个页面的规模不需要框架，重写还会带来全量回归。
- **用电平检测自动停止录音**：被否决。静音可能只是停顿，
  自动停会打断朗读；提示但不打断是正确尺度。
- **用 SSE/WebSocket 做管理端实时推送**：被否决（见 Reason）。
- **把员工名单/未交名单顺带做了**：被否决。属于 Phase 2 且需要用户提供名单，
  不在"UI/UX 优化"授权范围内。

## Consequences

- 员工端会在成功进入录音步后写一条 `localStorage`（姓名字符串）；
  清除浏览器数据后会重新要求输入。
- 提交路径从 `fetch` 变为 XHR，回归测试必须覆盖全部错误分支。
- 新增只读 Web Audio 分析链路，需在验收时实证录音约束与产物格式未受影响。
- 管理端每 30 秒产生一个 `GET /api/admin/submissions` 请求（后台暂停）。
- spec-002 编号与验收标准见 `specs/spec-002-ui-ux-polish/`。
